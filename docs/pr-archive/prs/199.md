1. **판정 틀 읽기** (`1ec5603`): 맞춤 목록이 판정 캐시에 없는 공고의 payload를 읽을 때 상세 화면용 큰 칸(근거·자격 원문·서류·선정 기준·안내·일정·문서·출처·입력)을 빼고 읽어요. 공고 300개 기준 DB가 보내는 양 48MB → 15MB, 쿼리 1.15초 → 0.35초.
2. **혜택 나이 미리 거르기** (`df55ec9`): 출생 연월이 있으면 DB가 「어느 한 그룹이 모두 값을 아는 나이 조건이고 가장 어린·많은 나이 모두 범위 밖」인 혜택을 골라 조건·지원 내용을 읽지 않고 판정도 하지 않아요(BenefitJudge와 같은 규칙). 지원 불가 개수에는 그대로 세요. 로컬 더미 열린 혜택 3,363개 중 22세 277 · 29세 317 · 35세 435 · 45세 1,529 · 68세 2,031개를 덜 읽어요.
3. **공고 시도 필터 인덱스** (`ea351eb`): `left(sigungu_code, 2) in (…)`가 지역 인덱스를 못 타던 것 → `notice.notice_regions (left(sigungu_code, 2), notice_id)` 식 인덱스(V202610312300). 쿼리는 그대로예요.
4. **관심 목록 N+1** (`b98c1a6`): 혜택·창업지원 사업·사업공간 모집을 한 줄씩 묻던 것 → 종류마다 한 번에. 한 페이지 쿼리 최대 22번 → 4번.

### 응답이 바뀌지 않는지 (테스트)
- 1: 칸을 줄여 읽은 판정 틀(가격 포함)이 payload 전체로 만든 것과 같은지
- 2: 나이 경계(그달 1일생·말일생), 같은 그룹의 다른 조건·나이 둘, 다른 그룹, min·max 하나만, 소수·문자 값, 값 모름, 안내 조건, 검수 중 혜택을 섞어 지원자 다섯 명·출생 연월 없음으로 「DB에서 거른 판정」 = 「모두 읽고 판정」. 걸러진 혜택이 지원 불가 개수에 들어가는지. 규칙을 일부러 틀리게 바꾸면 이 시험이 실패하는 것도 확인했어요
- 3: 시도 필터 식이 새 인덱스를 쓸 수 있는지 (쿼리는 그대로)
- 4: 한 번에 읽은 요약이 하나씩 읽은 것과 같은지(혜택·정책, DB), 관심 목록이 한 줄씩 묻지 않는지
