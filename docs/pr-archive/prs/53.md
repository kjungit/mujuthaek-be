### 무엇을
판정 엔진을 API로 여는 PR이에요. (REST 스택 7/7, [#52](52.md) 위에 쌓음) 모두 판정 입력이 섞여서 POST이고, **저장하지 않고 `Cache-Control: no-store`**예요.

| 메서드 | 경로 | 하는 일 |
| --- | --- | --- |
| POST | `/api/v1/eligibility/notices/{id}/evaluate` | 공고 판정: 공급 대상별 결과, 조건별 근거, 주택형별 준비할 돈 |
| POST | `/api/v1/eligibility/prepare-cost` | 보증금 하나로 준비할 돈 |
| POST | `/api/v1/notices/search` | 맞춤 목록: 공고마다 판정·준비할 돈, 정렬, 개수 |

- **공고 판정** `{ applicant }` → `{ noticeId, overall, reason, targets: [{ id, name, overall, summary, items }], missingInputs, unitTypes: [{ houseType, eligible, prepareCost }] }`
  - notice의 현재 공개 버전에 든 판정 틀(`extraction.completed`의 `judgment`)로 판정 (eligibility → notice, `NoticeQueryService.judgingSource`)
  - 판정 틀이 없는 공고는 `NEEDS_INPUT`과 이유 "공고 원문의 자격 조건을 확인해 주세요"
  - 인쇄된 소득표가 없으면 기준값(기준 중위소득 등)으로 상한 계산
- **준비할 돈** (`eligibility/rule/PrepareCost`): 보증금 − 받을 수 있는 대출 중 가장 큰 금액
  - 대출 상품 표 `eligibility.loan_products` (`V202610220345`): 한도, 보증금 대비 비율, 가구 연소득·총자산 상한, 나이, 대상
  - 나이·대상이 안 맞거나 모르면 그 상품은 안 씀. 소득·자산을 몰라 판정할 수 없는 상품이 더 많이 빌려주면 금액 대신 `INCOME_UNKNOWN`·`ASSET_UNKNOWN`, 금액이 없으면 `PRICE_NOT_ANNOUNCED`
  - `shortageWon`: 가용 현금을 넣었을 때만, 모자란 금액(넉넉하면 0)
- **맞춤 목록** `{ filters, applicant, sort, includeIneligible, cursor, size }`
  - 필터로 먼저 줄이고(기본 접수예정·접수중, 최대 300개) 공고마다 판정 → `RECOMMENDED`(지원 가능 → 확인 필요 → 지원 불가, 같으면 마감 임박) · `DEADLINE` · `PREPARE_COST`
  - 지원 불가는 기본으로 빼고, `counts { eligible, needsInput, ineligible }`는 빼기 전 개수
  - 한 줄: 공고 값 + `overall` + `prepareCostWon`(주택형 중 최소) + `prepareCostNote`

### 왜
- **판정 경로 B**대로 판정은 `/eligibility/…` 아래에 모았어요. 맞춤 목록은 설계 문서 경로(`/notices/search`)를 그대로 쓰지만 코드는 eligibility에 있어요. notice → eligibility 호출이 규칙상 금지라서, 판정을 부르는 쪽(eligibility)이 목록을 만들어요.
- **대출 상품 값은 아직 없어요.** 한도·조건은 관리자가 넣는 값이라 마이그레이션에 상품을 박지 않았어요. 상품이 없으면 준비할 돈 = 보증금이에요.
- 아직 없는 것: 주택형별 대상 구분(`unitTypes[].eligible`은 지금 공고 전체 결과), 맞춤 목록의 `areaScore`·`tags`·`favorite`(생활권 점수·로그인 차례), 판정 응답의 `area`·`regionalBenefits`(area·benefit 차례), 사업공간·혜택 판정.
- 맞춤 목록은 판정이 계산값이라 후보 300개까지만 보고, 목록 안 위치를 커서로 써요. 공고가 아주 많아지면 판정 결과 캐시가 필요해요.
