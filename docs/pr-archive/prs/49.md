### 무엇을
extraction이 보내는 `extraction.completed`를 받아 공고로 저장하는 부분이에요. (REST 스택 3/7, [#48](48.md) 위에 쌓음)

- **테이블** (`V202610220300__notice_store.sql`)
  - `notice.notices`: 공고 하나. 목록·검색에 쓰는 값(분야, 제목, 기관, 공고 유형 코드·원문 공급 유형, 시군구, 접수 기간, 공고일, 요약, 원문 주소), 공개된 현재 버전과 그 원본, 검수 승인본 여부, 숨김
  - `notice.notice_sources`: 받은 원본 버전 (`rawPostId`, `rawVersion`)마다 글 종류·검수 상태·공고 버전 번호·**payload 전체(jsonb)**. 상세 화면은 이걸 그대로 써요
- **수신** `notice/event/ExtractionCompletedListener`: 큐 `mujuthaek.extraction.completed`(+ `.dlq`)를 api가 만들고, `EventInbox`로 한 번만 처리
- **저장 규칙** `notice/service/NoticeIngestService`
  - 공고 찾기: 이미 받은 원본(이전 버전 포함) → 정정·후속이면 원래 공고(상세의 `sourceReferences[].supersedesPostId`) → 없으면 새 공고
  - `IN_REVIEW`는 저장만 하고 지금 공개된 버전을 유지 (처음부터 검수 대기면 공개 전)
  - `FOLLOW_UP`(후속 안내)는 원래 공고에 붙여 두기만 함
  - 더 새로운 원본이면 공고 버전 +1로 공개 / 같은 원본 버전을 다시 받으면(검수 승인 재발행) 내용만 바꾸고 `APPROVED`면 `reviewed = true` / 같은 원본의 예전 버전이 늦게 오면 저장만
  - `POLICY`·`STARTUP_SUPPORT`는 notice가 받지 않음
- **공고 유형 코드** `NoticeType`: 원문 공급 유형(매입임대 …)에서 API 설계의 코드(`PURCHASE_RENTAL` …)로. 못 찾으면 null이고 원문은 남겨요
- **접수 상태** `NoticeStatus`: 저장하지 않고 조회할 때 계산 (`ALWAYS` 시작·마감 없음 / `CLOSED` 마감일 지남 / `UPCOMING` 시작 전 / 그 밖 `APPLYING`), D-day, 목록 필터용 같은 규칙의 SQL 식
- **이벤트**: 처음 공개 → `NoticePublished`, 정정으로 목록 값이 바뀜 → `NoticeUpdated(바뀐 칸)`. 검수 승인 재발행은 알리지 않음 (사람이 확인한 것뿐이라)
- 공통: `UuidV7`(API ID 형식), `EventInbox.handleOnceWithEnvelope`(eventId가 필요한 수신기용), 수신 재시도 3번 → 실패 큐, 컨텍스트 테스트는 수신기 자동 시작 끔

### 왜
- 계약 README의 방침대로 notice는 `extraction.completed`의 `notice`를 버전별 스냅샷으로 저장하고, 목록·검색은 따로 뺀 칸(지역 5자리·유형·기간)을 써요. 상세 칸(단지·주택형·일정·조건)을 테이블로 다 나누지 않아서, 계약이 바뀌어도 저장은 그대로예요.
- extraction은 이 큐를 직접 만들지 않아서 api가 만들어요. **api가 한 번도 뜨지 않은 브로커에서는 extraction의 발행이 거절될 수 있으니**(발행기 mandatory) 배포 순서에 주의가 필요해요.
- **머지 순서 주의**: area 스택([#43](43.md)~[#46](46.md))의 마이그레이션 `V202610220215`이 이 스택의 `V202610220255`·`V202610220300`보다 시각이 앞서요. 이 스택이 먼저 배포되면 나중에 들어오는 area 마이그레이션을 Flyway가 순서가 틀렸다고 막아요. **area 스택을 먼저 머지**하거나, 그게 안 되면 area 쪽 파일 이름 시각을 머지 전에 뒤로 바꿔야 해요.
