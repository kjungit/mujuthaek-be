### 배경 (운영 장애)
area 적재 중 api의 `mujuthaek.area.source-ready` 수신기가 끊겼어요(consumers 0, 대기 13). `load_runs`의 ADDRESS_ENTRANCE 27은 8시간 RUNNING으로 남았고, api를 재시작해 이어서 처리했어요.
같은 때 api 로그에 「검수 API에 연결하지 못했어요」와 「수집기 관리자 API 503」이 반복됐고, 운영 `raw.policy.dlq`에는 4건이 쌓였어요.

### 원인
1. **수신기 끊김**
   - 수신기가 Spring 기본 설정이었어요: 메시지를 250개까지 미리 받고, 작업이 끝나야 ack하고, 소비자는 1개.
   - 그래서 도로명주소 16건을 한꺼번에 받아 하나씩 적재했고, 뒤 메시지들이 30분 넘게 ack되지 않았어요.
   - RabbitMQ 4.1 기본 `consumer_timeout`(30분)에 걸려 브로커가 채널을 닫았어요.
   - 수신 스레드는 적재 안에 묶여 있어서 다시 붙지 못했어요. 27번과 그 뒤 12건이 큐로 돌아가 대기 13이 됐어요.
   - 적재 SQL과 DB 소켓에 시간 제한이 없어서, 27번 적재가 끝나지 않고 계속 기다렸을 가능성이 커요.
2. **RUNNING이 남음**
   - 멈춘 RUNNING을 정리하는 코드가 없었어요.
   - 같은 파일을 다시 올려도 eventId가 같아서(지문으로 정해짐) `processed_events`에 걸려 처리되지 않았어요.
3. **검수(8092)·수집기 관리자(8093) 연결 실패**
   - 운영 compose가 api에 두 서비스의 주소를 넘기지 않았어요.
   - 그래서 api가 자기 컨테이너 안의 localhost로 부르고 연결이 거부됐어요.
4. **Boot 4.1에서 무시되던 설정**
   - `spring.rabbitmq.listener.simple.retry.max-attempts`는 Boot 4.1에서 읽지 않아요(`max-retries`로 바뀜).

### 바꾼 것
#### api: area 적재를 대기열로 (`area/`)
- 마이그레이션 `V202610291500__area_load_queue.sql`
  - `load_runs`에 `PENDING` 상태와 `allow_shrink`·`attempts`·`next_attempt_at` 열을 더해요.
  - 같은 파일에는 기다리거나 도는 요청이 하나만 있게 부분 유니크 인덱스를 둬요.
  - 이전 방식에서 남은 RUNNING은 실패로 닫고, 아직 성공한 적 없는 파일은 한 번씩 다시 기다리게 넣어요(운영의 27번 포함).
- `AreaSourceReadyListener`
  - 적재하지 않고 `AreaLoadQueue.request`로 PENDING만 남긴 뒤 바로 끝내요(ack).
  - 같은 파일이 이미 성공했으면 SKIPPED로 남기고, 기다리거나 도는 중이면 넘어가요.
  - FAILED만 있는 파일은 다시 넣어요. 같은 파일이면 eventId도 같아서, eventId 대신 파일 기준으로 걸러요(`EventInbox.readPayload`).
- `AreaLoadWorker`
  - 전용 스레드 하나에서 차례로 적재해요. 수신기가 깨우고, 놓친 요청은 30초마다 다시 봐요.
  - 연결 오류는 1분·2분 뒤 다시 하고, 파일당 3번이 넘으면 FAILED로 두고 알려요.
  - api가 뜰 때 남은 RUNNING은 FAILED로 닫고 다시 넣고 알려요. EC2 자동 중지 뒤에도 이어서 처리돼요.
- `PostgresAreaBaseDataLoader`
  - `loadRun`: 대기열에서 꺼낸 실행 기록을 이어 써요.
  - 트랜잭션에만 `statement_timeout` 90분(설정 `mujuthaek.area.load.statement-timeout`)과 `lock_timeout` 10분을 걸어요.
- 다른 수신기도 미리 받는 수를 10으로(`prefetch: 10`), 재시도는 `max-retries: 2`(처음 1번 + 다시 2번, 원래 뜻과 같음)로 바꿔요.
