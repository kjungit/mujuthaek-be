### 무엇을
area 적재기가 다시 넣을 때 **내용이 같은 줄은 기준일(data_date)도 건드리지 않게** 해요. (area 적재 스택 5, [#46](46.md) 위에 쌓음)

- `PostgresAreaBaseDataLoader`: 같은 줄의 `data_date`만 이번 파일 기준일로 맞추던 UPDATE(`touch_facilities.sql`·`touch_stores.sql`)를 빼고 두 SQL 파일을 지웠어요 (변환 SQL 13 → 11개)
- 줄의 `data_date` 뜻: "그 줄이 마지막으로 바뀐 적재의 원천 기준일". 원천 파일의 기준일은 `area.load_runs.data_date`에 있어요
- 새 마이그레이션 `V202610221415__area_data_date_comment.sql`: `area.facilities.data_date`·`area.stores.data_date`에 위 뜻을 칸 설명(comment)으로만. **이미 적용된 `V202610220215`는 고치지 않았어요**

### 왜
실제 규모(상가 277만 줄)로 저장·조회 방식을 비교했을 때, 서울 상가 55만 줄 다시 넣기 22초 중 15.6초가 이 기준일 갱신이었어요. 내용이 같은 줄을 매번 다시 쓰는 비용이라 빼면 약 6초예요. 원천 기준일은 적재 기록에 이미 있어서 줄마다 둘 필요가 없어요.

#### 실제 데이터로 적재하다 찾은 것 2개 (이 PR에 같이)
- **파일에 없는 줄 지우기를 반영보다 먼저**: 반영 뒤에 지우면 같은 트랜잭션에서 방금 넣은 줄이 통계에 없어서(새 시도 첫 적재면 0줄로 봄) 지우기가 점포마다 `stage_norm`을 통째로 읽어요(중첩 반복). 경기 상가 67만 줄 첫 적재가 12분 넘게 지우기에서 멈춰 취소했어요. 먼저 지우면 이미 커밋된 줄만 보고 결과는 같아요 — 같은 경기 파일로 되돌리는 세션에서 재 보니 지우기 60초 넘음(시간 제한) → 5ms
- **성공한 적재의 `finished_at`**: 성공 기록은 데이터와 같은 트랜잭션이라 `now()`가 트랜잭션 시작 시각이어서 소요 시간이 늘 0초로 보였어요. `clock_timestamp()`로

#### ⚠️ 마이그레이션 순서 (팀과 정하기)
저장소에는 Flyway out-of-order 설정이 없어요(api `spring.flyway.out-of-order`, collector Flyway 명령 둘 다). 그런데 두 스택의 마이그레이션 시각이 서로 섞여 있어요.
- area 스택: `V202610220215`([#43](43.md)), `V202610221415`(이 PR)
- REST 스택: `V202610220255`([#48](48.md)), `V202610220300`([#49](49.md)), `V202610220335`([#52](52.md)), `V202610220345`([#53](53.md))

어느 스택을 먼저 머지·배포하든, **나중에 들어오는 쪽에 "이미 적용된 것보다 이른 버전"이 생겨** 기본값(out-of-order=false)에서는 앱이 뜨지 않아요. 둘 중 하나로 정해야 해요.
1. 나중에 머지되는 스택의 마이그레이션 파일 시각을 머지 직전에 다시 매기기 (머지 전이라 규칙 위반 아님)
2. `spring.flyway.out-of-order=true`를 켜기 (환경마다 적용 순서가 달라질 수 있음)
