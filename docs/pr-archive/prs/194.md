### 무슨 일
- 운영 area 적재에서 ADDRESS_ENTRANCE 12건(scope 28, 30, 31, 36, 41, 43, 44, 47, 48, 50, 51, 52)이 `load_runs`에 줄이 하나도 없어요(PENDING·SKIPPED도 없음).
- `area.source-ready` 큐는 비어 있고 DLQ도 0이에요.

### 원인
- **옛 버전 수신기가 처리 기록 없이 ack한 게 아니에요.** **RabbitMQ가 빈 데이터로 다시 시작해서** 큐 안의 메시지가 사라졌어요.
- 2026-10-29 12:23 KST 운영 릴리즈(v0.2.0, 실패 후 되돌림)에서 RabbitMQ 컨테이너가 **다시 만들어졌어요**(`Container mujuthaek-rabbitmq-1 Recreate`).
  - 그 배포가 서버에 보낸 compose의 로그 설정이 바뀌었기 때문이에요.
  - 릴리즈 실행 8번 중 RabbitMQ를 다시 만든 건 이 한 번뿐이에요.
- RabbitMQ는 `rabbit@<호스트 이름>` 폴더에 큐·메시지를 둬요. compose에 `hostname`이 없어서 호스트 이름이 컨테이너 ID였어요.
  - 그래서 컨테이너가 바뀌자 볼륨은 그대로인데 **새 빈 폴더**로 시작했어요.
  - api가 큐를 다시 선언해 큐는 있지만 비어 있어요. 이전 폴더는 볼륨에 남아 있어요.
- 같은 이유로 그때 **dev.mirror shovel 설정도 사라졌을 거예요**(관리 API로 만든 설정이라 같은 폴더에 있어요).
- 옛 수신기(v0.1.0)는 메시지를 받으면 적재 전에 `load_runs`에 RUNNING·SKIPPED 줄을 먼저 남겨요. 그래서 「줄이 하나도 없다」는 건 메시지를 아예 받지 못했다는 뜻이에요.
- 적재 요청 이벤트는 같은 파일이면 eventId가 같아서(원천·범위·지문) 수집기가 다시 보내지 않았어요.

### 고친 것
- **`hostname: rabbitmq`**(운영·개발 compose): 컨테이너가 다시 만들어져도 같은 데이터 폴더를 써요.
- **`area-upload --resend`**: 이미 아웃박스에 적은 이벤트도 `published_at = null`로 되돌려 relay가 다시 발행해요.
  - api(v0.2.1~)는 같은 파일이 이미 성공했으면 SKIPPED로, 기다리거나 도는 중이면 넘어가요. 그래서 **목록 전체를 다시 보내도 빠진 것만 적재돼요.**
- README
  - 「빠진 적재 다시 요청」: 명령, 빠진 것 찾는 SQL
  - 「RabbitMQ 데이터가 사라질 때」: 원인, `hostname`을 처음 넣는 배포 때 할 일
