### 무엇
혜택(정책) 저장의 첫 단계예요. 정책 추출 결과 계약을 JSON으로 확정하고, api benefit 모듈이 그 이벤트를 받아 저장하고, 상세를 공개 API로 줘요. 설계는 `contracts/schemas/policy-extracted.draft.md`·`benefit-condition-types.draft.md`를 그대로 따랐어요.

자격 판정·맞춤 목록(`POST /benefits/search`, `/benefits/{id}/evaluate`)은 다음 PR(eligibility)에서 해요. extraction의 BENEFIT 추출(지금은 건너뜀)은 이 계약에 맞춰 따로 붙여요.

### 계약
- `contracts/events/policy.extracted.v1.json`: 초안 2·3장 payload (source · supports · schedule · conditions · quality). 조건은 type 목록·`known=false`면 `value: null`
- `contracts/examples/policy.extracted.json`: 초안 5장 무주군 예시, manifest에 등록
- api가 수신 경계에서 이 스키마로 검사해요 (`processResources`에 포함)

### 저장 (benefit 모듈)
- 마이그레이션 `V202610261200__benefit_tables.sql`: 초안 4장 SQL 그대로 + `category`(화면 분야 HOUSING·ASSET·TRANSPORT)
- `PolicyExtractedListener`: 큐 `mujuthaek.policy.extracted`(+ .dlq), 같은 eventId 한 번만, 계약 위반은 실패 큐
- `BenefitIngestionService` (초안 "저장 규칙")
  - 처음 받은 `rawPolicyId` → 추가, 더 큰 version → 고치고 지원·조건 줄은 지우고 다시, 같거나 작은 version → 버림
  - 처음 저장한 범위 안 정책(`relevant` · 재처리 아님)은 `BenefitPublished`
  - 이번엔 주거 혜택(`field=BENEFIT`)만 저장해요. 창업지원은 지금처럼 `notice.policy_judgments`
- 상태 계산 (초안 순서): 범위 밖 HIDDEN → 상시 OPEN → 시작 전 UPCOMING → 마감 지남 CLOSED → 그 밖 OPEN. 매일 0시 5분 다시 계산하고 새로 마감되면 `BenefitClosed`
- 분야: 주거 지원(월세·보증금·구입 대출·집 제공·전입 지원금)이 있으면 주거, 아니면 출처 분류의 교통 → 교통, 자산·저축·금융 → 자산형성, 그 밖 주거
- 같은 정책이 여러 출처에 있어도 지금은 출처마다 한 줄 (합치기는 실제 데이터를 본 뒤)

### API
- `GET /api/v1/benefits/{id}`: header(제목·기관·분야·요약·지역·신청 상태 UPCOMING/APPLYING/CLOSED/ALWAYS·기간·D-day·`needsReview`), supports(금액은 **원**), 신청 방법·서류·문의, 자격 조건 원문과 근거, 원문·신청 주소. 숨김·없는 혜택은 404 `BENEFIT_NOT_FOUND`
- eligibility가 부를 조회 `BenefitQueryService`: `openForJudgment(regionCodes)` (숨김·마감 제외, 비면 전체, 있으면 전국 + 그 지역과 겹치는 혜택. 시도 2자리는 그 안 시군구와 겹쳐요), `forJudgment(id)`
