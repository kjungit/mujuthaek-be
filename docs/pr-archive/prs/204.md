### 무엇을
로컬 스트레스(`20261102-0429_stress_local-seed_local`)가 100명은 통과하고 200명에서 막혔어요. 원인은 DB 커넥션 풀이었어요: Hikari 10/10 사용, 대기 최대 89·52, 1회차 커넥션 얻는 시간 평균 181ms·최대 17.8초. 힙(17~19%)과 판정 캐시(적중 100%)는 문제가 아니었어요. 풀 크기는 그대로 두고(운영 RDS 한도), 요청이 커넥션을 쥐는 시간을 줄였어요.

#### 원인 찾기 (로컬 api, Hikari usage 지표로 API마다 30번 평균)
- `spring.jpa.open-in-view`는 이미 `false`예요.
- **`NoticeQueryService`에 클래스 전체 `@Transactional(readOnly = true)`** 가 걸려 있어서, 메서드 하나가 커넥션 하나를 처음부터 끝까지 쥐었어요. 쿼리 사이의 자바 작업과 묶음마다의 지역 이름 조회 동안에도요. 지도 요청은 97ms 중 한 번에 75ms를 쥐었어요.
- **열린 혜택 목록 쿼리가 DB 시간 1위**였어요(스트레스 중 평균 79ms). 혜택마다 조건을 다시 훑는 나이 하위 쿼리 때문이에요(로컬 실행 32~55ms → 빼면 12ms). 혜택 조건은 #200부터 앱이 캐시해 판정하므로 DB에서 미리 거를 이득이 없어요.

#### 고친 것
1. `acc660a` 공고 조회: 클래스 전체 읽기 트랜잭션을 걷어 쿼리마다 잠깐 빌리고 바로 놓아요. Postgres 기본(READ COMMITTED)은 문장마다 새로 읽어서 읽기 트랜잭션으로 묶어도 같은 시점을 보지 않아요. 다른 트랜잭션 안에서 부르면 지금처럼 그 커넥션을 같이 써요. 쓰는 메서드는 없어요. 지도 묶음(핀 300개 초과)의 지역 이름은 `displayNames`로 한 번에 읽어요.
2. `dfdfbca` 혜택 판정 목록: 나이 하위 쿼리를 빼고 판정에 쓰는 칸만 읽어요. 판정은 `BenefitJudge`가 같은 규칙으로 해요.
