### 무엇을
collector가 원천 파일을 S3 `area/`에 올린 뒤 보내는 `area.source.ready` 이벤트 계약과, api가 그걸 받아 적재하는 수신기예요. (area 적재 스택 3/4, [#44](44.md) 위에 쌓음)

- **계약** `contracts/events/area.source.ready.v1.json` + 예시 `contracts/examples/area.source.ready.json`
  - 봉투는 다른 이벤트와 같아요 (`eventId`·`eventType`·`schemaVersion`·`occurredAt`·`producer: collector`·`payload`)
  - payload: `source`(SUBWAY_STATION·BUS_STOP·SCHOOL·PARK·HOSPITAL·STORES), `scope`(상가는 시도 이름, 나머지는 `ALL` — 스키마로 강제), `s3Key`(`area/{source}/{기준일}/{영문 이름}.csv`), `sha256`, `dataDate`, 기록용 `fileName`·`rows`
  - **eventId만 팀 규칙(UUID v7)과 달리 UUID v5로 고정**: `uuid5(NAMESPACE_URL, "https://mujuthaek.kr/events/area.source.ready/{source}/{scope}/{sha256}")`. 같은 파일을 두 번 보내도 같은 ID라 받는 쪽이 한 번만 처리해요
  - 예시는 2026-10-22에 실제로 올린 강원 상가 파일 값이라 manifest에 `synthetic: false`로 넣고, manifest 설명도 그에 맞게 고쳤어요
- **공통 수신 도우미** `common/messaging` (api의 첫 RabbitMQ 수신이라 모든 모듈이 같이 쓸 것)
  - `EventEnvelope`, `EventInbox.handleOnce(message, 종류, 버전, payload 타입, 처리)`: 봉투 읽기 → `common.processed_events`에 있으면 건너뜀 → 처리 → 기록. 처리 중 예외면 기록하지 않아요. JSON이 아니거나 종류·버전·payload 모양이 다르면 재시도 없이 실패 큐로
  - `RabbitTopology`: exchange `mujuthaek.events`·`mujuthaek.dlx`(파이썬과 같은 이름), 큐마다 `<큐>.dlq` 실패 큐를 만드는 `queue()`
- **수신기** `area/event/AreaSourceReadyListener`: 큐 `mujuthaek.area.source-ready`
- `application.yml`: 수신 재시도 3번(2초 → 4초) 뒤 실패 큐

### 왜
- 원천 파일은 이미 S3에 있고, 적재를 시작시키는 방법이 이 이벤트예요. collector가 보내는 쪽은 다음 PR이에요.
- **실패 처리 규칙**
  - 적재 결과 `FAILED`(칸 없음, 잘린 파일 같은 파일 문제)는 다시 해도 같으니 처리한 것으로 기록하고 끝내요. 이유는 `area.load_runs.error`에 남아요
  - S3·DB 연결 오류처럼 예외가 나면 기록하지 않고 다시 시도 → 3번 뒤 `.dlq`
  - 적재 커밋 뒤 `processed_events` 기록 전에 멈춰 다시 받아도, 적재기가 (원천, 범위, 지문)으로 `SKIPPED` 처리해서 안전해요
- **수신기 위치**: api에 아직 수신기가 없어서 이게 첫 기준이에요. 모듈의 `event` 패키지에 두고, notice 등도 같은 자리에 두면 좋겠어요.
- 큐·DLQ 이름 규칙은 extraction(`mujuthaek.raw.collected` + `.dlq`, `mujuthaek.dlx`)과 같아요.
