### 무엇

맞춤 목록(`POST /api/v1/notices/search`)이 느리던 원인을 고쳤어요. 판정 계산이 아니라, 공고마다 DB를 따로 조회하는 코드가 원인이었어요.

- **판정 틀 한 번에 읽기:** 후보 공고마다 `judgingSource(id)`로 payload 전체를 읽던 것을 `judgingSources(ids)` 한 번으로 바꿨어요. payload에서는 `judgment`와 `notice`만 꺼내요.
- **판정 틀 기억:** 공고 ID·버전으로 기억해 둬요(최대 2,000개). 기억하는 건 공개 데이터뿐이고, 사용자 조건과 판정 결과는 기억하지 않아요. 새 버전이 오면 키가 달라져서 옛 값은 밀려나요.
- **기준값은 요청당 한 번:** 기준 소득과 대출 상품을 공고마다 다시 읽던 것을 `NoticeEvaluationService.evaluator(applicant)`로 한 번만 읽어요.
- **지역 이름 한 번에:** 목록 줄마다 `displayName`을 따로 조회하던 것을 `RegionQueryService.displayNames(codes)`로 바꿨어요. 공개 목록(`GET /notices`)에도 똑같이 적용돼요.
- **추출이 덜 된 공고는 확인 필요:** `quality.coverage.eligibility`가 `EXTRACTED`·`NOT_IN_SOURCE`·`NOT_APPLICABLE`이 아니면 빠진 조건이 있을 수 있어요. 그래서 지원 가능·지원 불가로 단정하지 않고 확인 필요로 답해요.
  - 목록에서 빠지지 않아요.
  - 조건별 결과(충족·불충족)는 상세에서 그대로 보여요.
  - reason은 "공고의 자격 조건을 다 읽지 못했어요. 공고 원문의 자격 조건을 확인해 주세요"예요.
- **버그 수정:** 공고 표만 있는 소득 조건(`standard: null`, 계약상 허용)이 후보에 있으면 `Map.of` null 키에서 NPE가 나서 맞춤 목록 전체가 500이었어요.
